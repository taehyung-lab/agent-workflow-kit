# 선택 안내와 검토 도구

이 폴더는 프로젝트에 그대로 설치된다. 매 세션 읽는 기준은 저장소 맨 위 `AGENTS.md` 이고, 이 폴더에는 선택할 때만 읽는 안내([guide.md](guide.md))와 도구 둘이 있다. 단계마다 자동으로 불리는 스킬은 없고, 키트가 등록하는 훅은 Claude Code 의 세션 시작 정보 훅 하나다(정보만, 아무것도 막지 않음). Codex 에는 키트 훅을 두지 않는다.

| 파일 | 역할 |
| --- | --- |
| [guide.md](guide.md) | 작업 지도·질문·독립 검토를 고를 때만 읽는 안내 |
| [wf-verify/verify.py](wf-verify/verify.py) | 요구 기록 검사와 완료 판정(record), 독립 검토 입력 묶기(prepare)·결과 판정(finish). 검토자를 띄우지 않는다 |
| [wf-context/context.py](wf-context/context.py) | 맥락 확인(읽기 전용): `inspect` 는 실경로·커밋·변경 파일 이름·설치 키트 버전·다른 worktree·작업 지도 제목을 낸다. `hook` 은 세션 시작 훅이 부른다 |

## 세션 시작 정보 훅

설치기가 프로젝트 `.claude/settings.json` 의 `SessionStart` 에 `context.py hook` 항목 하나를 둔다(다른 훅·설정은 그대로). `.codex/hooks.json` 에는 두지 않고, v3.2~v3.4 가 둔 키트 항목은 업데이트 때 지운다. 세션이 시작·재개·초기화·압축될 때 위 관찰 값을 추가 맥락으로 넣을 뿐이고, 요청을 해석하거나 승인·차단하지 않으며 늘 종료 코드 0 이다. python3·git 이 없으면 아무것도 내지 않는다. 파일 내용·diff·원격 URL·env 값은 내지 않는다.

- Codex 는 프로젝트 훅을 경로·명령마다 따로 신뢰받아야 실행하고, 신뢰 전에는 경고 없이 건너뛴다. 그래서 새 워크트리·자동 실행에서는 정보를 넣지 못하고 확인창만 늘렸다. Codex 와 SessionStart 훅이 없는 도구에서는 시작·대상 변경·재개 때 `python3 .agents/skills/wf-context/context.py inspect` 를 직접 실행한다(guide.md 「맥락 봉투」).
- 대상이 바뀌는 순간(다른 폴더로 옮김, 가지 전환)에는 훅이 돌지 않는다. 그때는 위 명령으로 다시 확인한다(guide.md 「맥락 봉투」).
- 이 값은 "어디서 일하는가"의 관찰일 뿐이다. 읽은 자료를 현재 사실로 잘못 쓰는 것, 다른 프로젝트 정책을 끌어오는 것은 막지 못한다. 그 판단은 AGENTS.md 기본 1 이 맡는다.

## 누가 무엇을 맡나

- **요청을 어떻게 이해하고 어디까지 할지**: 에이전트가 AGENTS.md 기준으로 판단한다. 분명한 실행 요청은 바로 하고, 조사·설명·리뷰 요청은 고치지 않고, 결과가 갈리는데 근거로 정할 수 없는 선택만 묻는다.
- **파일 쓰기·명령을 실제로 허용할지**: 각 도구의 권한 설정과 sandbox 가 맡는다(Claude Code 의 permissions, Codex 의 sandbox·승인 정책). 확인 창이 뜨는지는 사용자 설정을 따르고, 키트는 자기 확인 단계를 더하지 않는다.
- **결과가 맞는지**: 검사·diff 검토와, 필요할 때 아래 독립 검토가 본다.

v3.0 까지 있던 승인 관문 훅(`wf-design/approval-gate.py`)은 v3.1 에서 없앴다. 업데이트하면 설치기가 그 파일과 프로젝트 설정의 관문 훅 항목만 지운다(루트 README 「업데이트」). v3.2 의 정보 훅은 관문이 아니다: 쓰기·명령 허용은 여전히 각 도구의 권한 설정이 맡는다.

## 요구 기록 검사와 독립 검토 도구

`verify.py record --map <지도> [--check <직접 검사 결과>]` 는 작업 지도 `## 기준` 을 읽기만 한다: `요청 원문` 항목이 있는지, 요구 기록 표의 형식(상태 값, 확정인데 출처 없음, 미정·미확인에 의존하는 확정 행)이 맞는지 보고, 독립 검토 없이 전체 완료(`completion`)를 낸다. 형식 문제는 `returned`(지도를 고친다), 미정 행이 남으면 `waiting-user`, 미확인 행이 남거나 직접 검사 결과를 받지 않았으면 `unverified` 다. 출처가 정말 그 결과를 정하는지는 이 명령이 판단하지 못한다(그 판단이 필요하면 독립 검토). 독립 검토가 필수인 작업의 완료는 아래 `prepare`·`finish` 가 판정한다.

`verify.py prepare` 는 **요청 원문**(작업 지도 `## 기준` 의 `요청 원문` 항목, 또는 `--request` 로 준 사용자 글 그대로), **작업 지도의 `## 기준`·`## 맥락`**(있으면), **맥락 도구가 관찰한 대상 저장소 정보**, **기준 커밋부터의 변경**(diff, `--base`, 기본 HEAD)을 묶고 판정 대상을 고정 복사본으로 만든다. 분석·설계·질문만 한 작업은 `--output <파일>` 로 산출물을 넘기면 검토자가 그 산출물의 대상·전제·인용이 원문·맥락과 맞는지 본다. 요청 원문을 확보하지 못하거나, 지도 기준이 비거나, 바뀐 파일도 산출물도 없으면 입력 부족(미확인)으로 끝나며, 요약한 계획으로 대신하지 않는다. 검토자는 하네스의 하위 에이전트이고, 그 마지막 답을 `verify.py finish --round <kept> --check <직접 검사 결과>` 가 형식대로 판정한다. 전체 완료(`completion`)는 검토·직접 검사·작업 지도 요구 기록의 미정(사용자 답 대기)·미확인을 합쳐 모두 확인됐을 때만 `verified` 다. `prepare` 가 읽은 근거(제품 파일, 원문·조건·산출물 파일, 지도 `## 기준`·`## 맥락`)는 한 기록으로 남겨 `finish`·끝난 회차 재조회·한도 뒤 재사용 때 현재와 대조한다. `work/` 안 파일도 같다. 지도의 기준·맥락은 사용자 원문이 아니라 구현자의 해석으로 넘어가며, 검토자는 원문과 대조한다.

`prepare` 는 그 밖에 `--conditions <파일>`(사용자·평가자가 따로 정한 필수 조건, 줄 머리·표 첫 칸의 ID 가 필수 조건이 된다)과 `--rounds <n>`(재검토 한도, 기본 2)을 받는다.

결과: `finish` 의 `ok`(0)만 검토 통과(`record` 의 `ok` 는 형식이 맞다는 뜻이고 결과에 `review: off` 가 붙는다), `returned`(3) 원인 자리로 돌아가 고친 뒤 다시, `incomplete`(4) 재검토 한도, `unverified`(5) 빈 답·형식 오류·검토자가 대상을 바꿈·검토 근거 변경(위 대조에서 다르거나, 근거 기록이 없는 옛 회차)·입력 부족. 회차 기록은 지도 옆 `verify/` 또는 `work/review/` 에 남는다. 사용 절차는 guide.md 「독립 검토」.

한계: 지도에 옮긴 요청 원문이 사용자 글 그대로인지는 도구가 확인하지 못한다(옮기는 사람이 줄이지 않고 인용한다). 작업 전부터 있던 미커밋 변경은 기준 커밋부터의 diff 에 섞인다. 추적하지 않는 새 파일은 무시 목록(.gitignore)에 없으면 판정 대상에 들어가지만, 파이썬 캐시(`__pycache__`·`.pyc`)는 검사 실행마다 바뀌므로 무시 목록이 없어도 넣지 않는다. 재검토 한도는 같은 요청 원문·기준 커밋 안에서 센다.

모델 없이 검토 도구를 확인하는 시험은 키트 저장소의 `evals/flowtest.py`·`evals/sandboxtest.py` 에 있다.
