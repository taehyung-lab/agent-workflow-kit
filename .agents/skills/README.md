# 단계 스킬과 승인 관문

이 폴더는 프로젝트에 그대로 설치된다. 에이전트가 일의 단계마다 꺼내 읽는 **단계 스킬** 세 개와, 사용자 승인 없이 수정 도구로 코드를 쓰지 못하게 막는 **승인 관문 훅** 하나가 들어 있다.

매 세션 읽히는 작업 기준은 저장소 맨 위 `AGENTS.md` 다. 이 폴더의 스킬은 그 기준이 "이 단계가 필요하다"고 판단할 때만 읽힌다. 작은 일은 스킬 없이 끝난다.

## 단계 스킬: 언제 무엇을 읽나

| 스킬 | 언제 읽나 | 하는 일 | 예 |
| --- | --- | --- | --- |
| [wf-design](wf-design/SKILL.md) | 요구·연결 영향·해법이 아직 정해지지 않았을 때 | 근거를 찾아 조건(무엇을 어디서 확인하면 끝인지)을 정하고, 정해지지 않은 결과는 추천과 함께 묻는다 | "상품 카테고리 관리 화면을 만들어 줘": 추가·삭제를 넣을지, 쓰는 중인 카테고리를 지울 수 있게 할지 묻는다 |
| [wf-implement](wf-implement/SKILL.md) | 확정된 설계를 받아 구현하거나, 돌려받은 결함을 고칠 때 | 가장 작은 변경을 실제로 쓰는 곳까지 잇고, 조건마다 실제 결과와 증거를 남긴다 | 승인된 설계대로 저장 오류를 고치고, 고치기 전 실패·고친 뒤 통과를 남긴다 |
| [wf-verify](wf-verify/SKILL.md) | 공용 경계를 바꾸거나 틀리면 영향이 큰 변경을 **구현하지 않은 쪽**이 판정할 때 | 원문·확정 조건·변경물만 받아 조건별로 충족·미충족·미확인을 판정한다 | 회계 시스템이 그대로 읽는 내보내기 형식을 바꾼 변경을 별도 세션이 판정 |

`wf-design/work-template.md` 는 **작업 지도**(`work/<작업명>/work.md`)의 양식이다. 요구·결과·변경 위치·영향받는 기존 보장·확인 방법을 한 곳에 두고, 승인 대상인 `## 기준`과 실행 결과인 `## 증거`를 나눈다. 계획·검증지·인계 문서를 따로 만들지 않는다. 작은 일은 몇 줄이다.

## 승인 관문: 무엇을 막고 무엇은 막지 않나

[wf-design/approval-gate.py](wf-design/approval-gate.py) 는 설치기가 프로젝트의 `.claude/settings.json`(Claude Code)과 `.codex/hooks.json`(Codex)에 등록하는 훅이다. 하네스가 세 시점에 부른다.

```text
사용자 메시지 도착 ──▶ prompt: 이 메시지가 승인인지와 그때의 제품 파일별 지문을 기록("진행해 주세요"·"승인합니다"·"바로 고쳐 주세요")
도구 쓰기 직전   ──▶ pre:    승인이 없으면 수정 도구(Edit·Write·apply_patch 등)를 거절하고, 계획을 보여 주고 물으라고 알려 준다. 셸은 보지 않는다
답을 마칠 때     ──▶ stop:   승인이 없었는데 제품 파일이 바뀌었으면 바뀐 파일 이름을 알린다(관문은 되돌리지 않는다)
```

| 승인 전에도 되는 것 | 승인이 있어야 되는 것 |
| --- | --- |
| 파일 읽기·검색, 모든 셸 명령(어느 언어의 검사든: `go test`·`composer test`·`./gradlew test`·`pnpm test`·`python3 -m pytest` 등) | 수정 도구로 제품 파일 쓰기(Edit·Write·MultiEdit·NotebookEdit·apply_patch), 이름으로 쓰기임이 드러나는 도구(MCP 파일 쓰기 등) |
| `work/` 아래 작업 지도 쓰기 | 셸로 제품 파일을 바꾸는 것도 승인이 필요하다. 다만 미리 막지 않고 턴 끝에 드러낸다 |

- **사전 차단은 수정 도구뿐이다. 셸 쓰기는 사후 감지다.** 셸 명령의 뜻을 해석하는 판별(명령 목록·언어별 검사식·캐시 예외)은 없다. 감지 시점에는 이미 쓰기가 일어났으므로 "승인 전에 제품 파일이 바뀌지 않는다"는 사전 보장이 아니다.
- **감지 범위**: git 이 아는 파일과 무시되지 않은 새 파일의 내용·실행 권한·하위 저장소 버전(키트·하네스 설정·`work/` 제외). 무시된 파일·저장소 밖·외부 효과(배포·네트워크·데이터베이스)는 보지 않는다. 빌드 산출물·캐시는 프로젝트 `.gitignore` 가 정한다(무시하지 않은 생성물은 변경으로 알린다).
- **사용자 변경 보존**: 턴 시작 전부터 있던 미커밋 변경은 알림 대상이 아니다. 턴 도중 사용자·다른 작업이 바꾼 파일은 구별하지 못해 알림에 섞일 수 있다. 그래서 관문은 아무것도 되돌리지 않고, 에이전트에게는 자기가 바꾼 것이 확실한 파일만 되돌리고 섞였으면 사용자에게 알리라고 한다(일괄 되돌리기 금지).
- **셸 허용은 외부 효과 허락이 아니다.** 배포·삭제·외부 서비스 쓰기는 AGENTS.md 「실행 경계」대로 요청이 허용한 범위에서만 한다.
- **승인은 지금 작업에 묶인다.** 관문은 세션마다 "지금 작업" 기록 하나(작업 id·승인 근거인 사용자 메시지·승인한 기준·이 작업의 사용자 원문 전부·검증 결과)를 `.git/awk-gate/` 에 둔다. 승인은 사용자 메시지로만 열리고, 상태 질문("어디까지 됐어요?") 같은 다음 메시지에도 유지된다. 철회("취소합니다")·승인 말이 든 부정·질문("승인하지 않습니다", "진행해 주세요?")은 닫는다.
- **기록의 위치와 작업 수명은 따로다.** 작업 기록은 지도 파일(`work/<작업명>/work.md`)이든, 승인을 물은 답에 보여 준 같은 양식의 `## 기준` 절이든 된다(관문은 하네스가 넘기는 대화 기록 경로로 마지막 답을 읽는다). 관문은 `## 기준` 절을 빈 줄·줄 끝 공백만 뺀 글로 비교해 "같은 기준인가"만 본다. 그래서 답으로 승인받은 기준을 지도로 그대로 옮기거나 지도를 다른 경로로 옮겨도 승인이 유지된다. 글이 다르면(같은 뜻을 다르게 쓴 경우 포함) 새 기준으로 보고 다시 묻는다. 대화 기록을 읽지 못하면 대화의 기준은 없는 것으로 본다(승인 뒤 처음 쓴 지도는 닫힌다).
- **승인 밖 기준이 나타나면 닫힌다.** 승인한 지도의 `## 기준` 절이 바뀌거나 사라지면(조건 추가·삭제·수정), 또는 이 세션이 승인 때 없던 기준(새 지도, 답에 보여 준 새 `## 기준`)을 내놓으면 수정 도구를 다시 막는다. 닫힘은 사용자가 다시 승인할 때까지 유지된다(에이전트가 기록을 되돌려도 열리지 않는다). 담당자·설계·`## 증거` 갱신은 유지된다. 승인 때 이미 있던 다른 작업의 지도가 바뀌는 것은 상관하지 않는다. 평가 실행기가 보낸 검증 반환처럼 사용자가 쓰지 않은 입력은 실행기가 `AWK_GATE_PROMPT_FROM=runner` 로 알려 승인 상태를 바꾸지 않는다. 지도에 "approved: true" 를 쓰거나 답에 "승인합니다" 를 써도 열리지 않고, 관문 기록을 수정 도구로 바꾸는 것은 막는다.
- **새 작업·완료는 에이전트가 선언한다.** 에이전트가 새 요청을 다른 작업으로 판단하면 `python3 .agents/skills/wf-design/approval-gate.py task begin <작업명>` 을 실행한다. 지금 승인이 닫히고 이번 턴의 사용자 원문부터 새 작업이 시작된다(이전 작업의 지도·원문·검증 결과는 넘어가지 않는다). 마치면 `task done` 으로 승인을 닫는다. 이 선언은 승인을 닫기만 하고 열지 못한다. 세션은 하네스가 셸에 주는 `CLAUDE_CODE_SESSION_ID`·`CODEX_THREAD_ID`(없으면 `--session`)로 고른다. `approval-gate.py status` 는 지금 작업의 상태(open·closed·waiting)를 보여 준다.
- **한계: 작업 전환은 에이전트 판단이다.** 사용자가 "이제 비밀번호 변경도 만들어 주세요"라고 해도 관문은 메시지 뜻을 분류하지 않으므로 그것만으로 닫지 않는다. 에이전트가 새 작업을 선언하거나 새 기준을 내놓으면 닫히지만, 새 요청을 기존 작업으로 잘못 보고 바로 쓰면 관문은 막지 못한다. 그 경우는 독립 검증자가 사용자 원문 전체와 대조해 잡아야 한다.
- **한계: 말로만 한 범위 변경은 관문이 막지 못한다.** 승인 뒤 사용자가 "그런데 재가입은 막아 주세요"처럼 범위를 바꿔도 관문은 메시지 뜻을 분류하지 않으므로 닫지 않는다. 에이전트가 기준에 반영해 내놓으면 닫혀 다시 묻게 되고, 반영하지 않은 채 구현하면 독립 검증자가 사용자 원문 전체와 대조해 돌려보내야 한다.
- **무엇을 승인으로 보나.** "진행해 주세요"·"승인합니다"·"바로 고쳐 주세요"·"go ahead" 같은 승인 말이 완결된 형태로 있고, 그 문장이 질문·부정이 아니면 승인이다. 어순과 범위 제한은 상관없다: "영어 문구 빼고 진행해주세요"와 "진행해주세요 영어 문구 빼고"는 둘 다 승인이다. "진행해도 될까요?", "진행해주세요라고 답하세요", "승인합니다. 아직 시작하지 마세요"는 승인이 아니다. 범위 제한을 지키는 것은 에이전트 몫이다.
- **관문은 분명한 승인만 연다. 애매함은 에이전트가 더 조심하는 쪽으로만 판단한다.** 예문 속 승인("답변 예문: 승인합니다")처럼 관문이 가리지 못하는 드문 말이 있어서, 승인 말이 있어도 뜻이 애매하면 에이전트가 쓰기 전에 다시 확인한다(AGENTS.md 2항). 에이전트가 "승인으로 봐도 된다"고 판단해 관문을 여는 일은 없다.
- **실수 방지 장치다.** 에이전트가 일부러 승인 기록이나 훅 파일을 고치는 것까지 막지는 않는다. 그것까지 막으려면 하네스의 읽기 전용 실행 모드를 함께 쓴다.
- **Codex 는 처음 한 번 신뢰가 필요하다.** 프로젝트 훅은 Codex 시작 화면에서 "신뢰"(`t`)를 고르거나 Codex 안에서 `/hooks` 를 열어 신뢰해야 돈다. 고르지 않으면 훅 없이 실행된다(문장 기준만 적용).
- **worktree·clone 을 자주 만들면 사용자 전역에 한 번 등록한다.** Codex 의 신뢰는 경로마다 따로 기록되어, 새 작업 공간마다 다시 골라야 한다. `~/.codex/hooks.json` 의 `UserPromptSubmit`·`PreToolUse`·`Stop` 에 아래 명령을 하나씩(끝 단어만 `prompt`·`pre`·`stop`) 더하고 Codex 에서 한 번 신뢰하면 모든 저장소에 적용된다. 키트가 없는 저장소에서는 아무것도 하지 않는다. 프로젝트 등록과 둘 다 돌아도 관문이 같은 턴 끝의 두 번째 호출을 같은 판단으로 처리한다.

  ```sh
  r=$(git rev-parse --show-toplevel 2>/dev/null) && [ -f "$r/.agents/skills/wf-design/approval-gate.py" ] && exec python3 "$r/.agents/skills/wf-design/approval-gate.py" pre; exit 0
  ```

- 판단 기록이 필요하면 환경 변수 `AWK_GATE_LOG=<파일>` 을 주면 판단마다 한 줄씩 남는다.

## 독립 검증 실행기: 별도 검증이 필요할 때

[wf-verify/verify.py](wf-verify/verify.py) 는 구현하지 않은 별도 세션(Claude Code 또는 Codex)을 띄워 판정받는 실행기다. AGENTS.md 「필요한 단계만」이 별도 검증을 요구할 때만 쓴다(작은 수정은 직접 확인).

```sh
python3 .agents/skills/wf-verify/verify.py --harness claude   # 또는 codex
```

- **넘기는 것**: 관문 기록의 이 작업 사용자 원문 전부(승인 메시지 포함)·승인한 기준·승인을 물은 답(계획)·작업 시작 상태(작업의 첫 요청이나 `task begin` 턴이 시작될 때의 제품 파일, 승인 때 덮지 않음)부터 지금까지의 변경(diff). 작업 전부터 있던 사용자 미커밋 변경은 빠지고, 요청 뒤 승인 전에 바뀐 파일은 보인다. 구현자의 답·지도의 `## 증거` 는 넘기지 않는다. 판정 대상은 커밋한 복사본으로 고정한다(무시된 파일·작업 지도·키트 설정은 넣지 않는다).
- **결과**: `ok`(종료 0)만 완료다. `returned`(3)는 원인을 고친 뒤 같은 명령으로 새 버전을 다시 판정받는다. `incomplete`(4)는 재검증 한도 도달이다. 한도(`--rounds`, 기본 2)는 그 승인의 첫 회차에 정해지고, 닿은 뒤에는 새 검증자를 띄우지 않는다(사용자의 새 승인이 새 시도를 연다). `unverified`(5)는 빈 답·형식 오류·필수 조건 누락·하네스 없음·검증자가 대상 파일을 바꿈·승인 기록 없음·작업 후보 여럿·근거 불완전(시작 내용 미보존·diff 실패·잘림)·검증하는 동안 작업이나 제품 파일이 바뀜(고정 대상의 판정은 target_state 로 남김)이다. 작업이 사용자 답을 기다리는 중이면(철회·기준 변경) 검증 OK 여도 완료가 아니다(waiting-user). 판정은 관문의 작업 기록에, 회차마다 고정 대상 저장소·시작 상태·전체 diff·입력·판정은 `.git/awk-gate/verify/task-<id>/round-N-<고유 이름>/` 에 회차마다 새로 남는다(기존 증거·`--keep` 폴더의 파일은 지우거나 덮지 않는다).
- **검증자의 글은 승인이 아니다.** 결과는 명령 출력으로만 돌아오고 사용자 메시지로 들어가지 않으므로 그 안의 "승인합니다"·"취소합니다"는 승인 상태를 바꾸지 않는다.
- **작업 고르기**: 하네스가 셸에 주는 세션 id 로 이 세션의 작업을 고른다. 세션 id 가 없으면 기록이 하나일 때만 쓰고, 여럿이면 추측하지 않는다(`--session` 으로 지정).
- 평가 실행기(`evals/run.sh`)도 같은 실행기를 쓴다. 다만 하네스가 실행기 밖에서 돌므로 사용자 원문·계획·기준·작업 시작 상태를 파일로 넘긴다.

모델 없이 관문 동작을 확인하는 시험은 키트 저장소의 `evals/gatetest.py` 에 있다(어느 언어의 검사 명령도 미리 막지 않음, 셸 쓰기 알림, 사용자 변경 보존 포함). 실제 설치본의 관문·검증 실행기를 가짜 하네스로 부르는 일반 설치 흐름 시험은 `evals/flowtest.py` 다.
