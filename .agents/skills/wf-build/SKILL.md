# 설계·구현

확정된 요구를 실행 가능한 설계로 바꾸고 하나씩 만든다. 무엇을 만들지는 요구가 정하고, 어떻게 만들지는 여기서 정한다.

## 절차

1. **요구마다 설계를 잇는다.** 기대 결과 → 필요한 상태·처리·책임 → 변경 위치 → 확인 방법. 같은 보장이 지나가는 다른 경로(다른 저장 경로·다른 화면·기존 자료)도 찾아 함께 잇는다.
2. **실행할 수 있는지 확인한다.** 필요한 자료·도구·권한·실행 환경이 있는지 본다. 쓸 수 없는 것이 있으면 구현할 수 있는 부분과 실제 확인이 막힌 부분을 나눠 밝힌다. 사용자 동의가 필요한 동작 변경을 임의의 우회로 대신하지 않는다.
3. **기대값을 보는 검사를 먼저 쓰고 실패를 본다.** 기대값은 요구에서 나오고 구현을 보고 정하지 않는다. 관찰 장소는 사용자가 쓰는 경로(공개 명령·화면·요청·저장된 값)다. 실패하지 않으면 검사가 요구를 보지 않는 것이니 검사를 고친다.
4. **그 검사가 통과할 만큼만 구현하고 전체 검사를 돌린다.** 요청 밖의 동작·표현은 그대로 둔다.
5. **요구들을 사용 흐름으로 이어 본다.** 예: 응답 유실 → 다시 시도 → 조회. 순서·동시 실행·이미 쌓인 자료가 요구를 깨는 경우를 실제로 돌려 보고, 깨지면 3으로 돌아간다.
6. **새 제품 선택을 만나면 정하지 않는다.** 사용자가 받는 결과가 갈리는데 근거가 없는 선택이 나오면 `wf-ask` 로 돌아가 결정으로 묻는다. 구현 방법의 선택은 여기서 정한다.

## 끝 조건

요구마다 먼저 실패했던 검사가 통과하고, 바꾼 코드가 지키던 기존 검사가 통과한다. 요구별 설계·실행한 명령·실제 출력을 남긴다(작업 지도가 있으면 「설계·검증」에 요구 ID 로).
