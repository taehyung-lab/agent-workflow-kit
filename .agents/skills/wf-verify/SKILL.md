# 결과 검토

판정의 근거는 요청 원문·사용자 결정·계약과 실제 관찰이다. 구현자의 자기평가는 근거가 아니다.

## 절차

1. **원문에서 결과물로 대조한다.** 요청 원문과 사용자 답을 다시 읽고, 거기서 요구한 것이 결과물에 모두 있는지 본다(작업 지도의 요구만 보지 않는다: 지도에서 빠진 요구도 여기서 찾는다). 요구마다 실행한 명령과 실제 출력으로 확인하고, 바꾼 코드가 지키던 기존 보장도 같다. 확인하지 못한 것은 사유·재개 조건과 함께 미확인으로 남긴다(빼거나 낮추는 것은 사용자가 정한다).
2. **결과물에서 근거로 대조한다.** 결과에 들어간 동작마다 그것을 정한 근거(원문·사용자 답·계약)가 있는지 본다. 근거 없이 내가 정한 동작이 있으면 완료가 아니다. `wf-ask` 로 돌아가 결정으로 묻는다.
3. **기록과 실행 증거를 대조한다.** 지도가 있으면 `python3 .agents/skills/wf-verify/verify.py record --map <지도>` 로 연결 누락과 남은 결정을 확인한다. 종료 0은 기록 구조가 유효하다는 뜻이다. 각 요구의 실제 결과를 1·2에서 확인하고, 미해결·미확인 사항이 있으면 원인 단계로 돌아간다. 도구의 기록 통과로 이 대조를 대신하지 않는다.
4. **독립 검토를 받는다.** AGENTS.md 기본 4가 정한 작업(사용자 요구, 검사 약화, 외부 시스템이 읽는 형식·계약 변경)은 반드시 받는다. 그 밖에는 어떤 보장이 깨질 수 있는데 직접 확인만으로 확인하기 어려울 때 골라서 받는다(그 이유를 한 줄로 밝힌다).
   1. `verify.py prepare --map <지도>` (지도가 없으면 사용자 글 그대로를 `--request <파일>`, 작업 전 커밋이 HEAD 가 아니면 `--base <커밋>`, 분석·설계 산출물이나 구현자 보고·명령·출력은 `--output <파일>`). 답이 제안을 가리키면 실제 보낸 제안과 답도 지도 또는 `--output` 대화 기록으로 함께 전달한다. 입력이 모자라면 미확인이다(요약으로 대신하지 않는다).
   2. `prompt_file` 을 그대로 하위 에이전트(검토자)에게 맡긴다.
   3. 검토자의 마지막 답을 고치지 않고 `verify.py finish --round <kept> --check <직접 검사 결과>` 의 표준 입력으로 넘긴다.
   4. returned 면 사유를 원문·기준과 대조해 원인이 있는 단계로 돌아간다(요구는 `wf-ask`, 설계·코드·검사는 `wf-build`). 고친 뒤 prepare 부터. incomplete 는 미완료, unverified 는 사유·재개 조건과 함께 보고한다.

## 끝 조건

원문·사용자 답에서 합의한 결과를 실제 동작으로 확인했고, 미해결 결정·실패·미확인이 없으며, 독립 검토가 필수인 작업은 검토까지 통과했다. 그렇지 않으면 완료라 하지 않고 남은 것을 그대로 알린다.

## 검토자 기준

판정 범위는 바꾼 동작·산출물과 연결 근거가 있는 기존 보장이다. 원문·사용자 결정·계약으로 정한 결과와 실제 동작을 대조한다. 조사 사실은 제안의 적합성을 뒷받침하며, 제안한 결과의 승인은 보낸 제안과 사용자 답에서 확인한다. 새 요구가 있어야 성립하는 반례는 범위 밖으로 따로 적는다.
