# 검증과 실패 회수

1. 원문·사용자 결정에서 기대 결과를 확인한 뒤 설계·조건·변경물과 대조한다. 누락된 기존 요구는 복원하고 새 범위는 별도로 표시한다.
2. 코드·실행 대상·환경·데이터가 같은 작업을 가리키는지 확인한다. 승인된 조건이나 제품 코드를 판정 중 임의로 바꾸지 않는다.
3. 필수 조건과 연결 영향을 실제 관찰해 충족·미충족·미확인으로 기록한다. 실환경이 필요한 결과를 대역 성공으로 닫거나 공용 코드 결함이라는 이유로 제외하지 않는다.
4. 신규·수정 수용 검사의 정상·위반 사례 판별 근거를 확인하고 의심되는 판정은 독립 재현한다. 반례는 허용된 격리 환경에서 다루며 다른 작업자의 작업물을 훼손하지 않는다.
5. 실패에는 재현·기대와 근거·실제 결과를 남기고 요구·설계·구현·검사·환경·미상 중 확인한 원인을 고른다. 설계에 구현 수단이 적혀 있지 않다는 이유만으로 설계 결함이라 단정하지 않는다.
6. 원인 소유자에게 수정과 재확인 범위를 넘기고 실패·수정 영향·기존 미해결을 다시 확인한다. 이전 성공은 영향과 대상·근거의 유효성을 확인한 때만 이유를 붙여 재사용한다.
7. 재사용 개선은 코드·검사·지도·해당 스킬·권한 설정 중 원인이 있는 곳에 반영한다. 실패 대응으로 방법 문장을 바꾸면 추적 가능한 출처·날짜·재검토 조건을 붙이고, 다른 작업의 효과는 실제 재사용과 비교 근거의 범위만 보고한다.
8. 전체 담당자에게 조건별 판정·근거·미해결을 넘기며 필수 미충족·미확인이 있으면 완료하지 않는다. 완료 보고와 정본 반영 후 해당 작업의 임시 자료만 정리하고, 한도 종료·답변 대기 자료는 보존한다.
