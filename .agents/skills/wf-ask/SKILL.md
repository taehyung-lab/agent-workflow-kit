# 요구 확인

이 단계의 산출물은 코드가 아니라 **사용자에게 보내는 이해 확인**이다. 사용자가 확인하기 전에는 제품 파일을 고치지 않는다(조사·재현·실행은 한다. 무관해 보이는 부분도 먼저 구현하지 않는다).

## 절차

1. **조사한다.** `python3 .agents/skills/wf-context/context.py inspect` 로 지금 대상(경로·커밋·변경)을 보고, 요청 원문·계약·환경 문서·현재 동작을 읽고 실행해 본다. 조사로 알 수 있는 사실은 묻지 않는다. 과거·참고 자료는 현재 파일과 대조한 뒤에만 쓴다.
2. **내가 정한 것을 전부 편다.** 요청의 목표 문장을 구절로 나누고, 구절마다 "어떤 입력에서 사용자가 어디서 무엇을 보게 되는가"로 옮긴다. 옮기면서 내가 고른 것을 종류와 함께 적는다.
   - 읽기: 원문 낱말을 코드·자료의 무엇으로 읽었는가. 예: "같은 신청" → 요청 ID 가 같은 것. 계약이나 현재 코드와 맞는 읽기도 읽기다.
   - 그대로 두기: 규칙이 없어서 지금 동작대로 두기로 한 것.
   - 선택: 원문·사용자 결정·외부 계약에 근거가 없는 값·정책.
3. **사용 흐름에 대입해 거른다.** 항목마다 달리 정했을 때 사용자가 보게 될 차이를 실제 흐름(다른 기기·다시 시도·이미 쌓인 자료·동시 사용)에 넣어 한 줄로 적는다. 차이가 없으면 구현 세부이니 지운다. 원문이 그 결과를 글자 그대로 말한 항목도 지운다.
4. **남은 항목을 한 번에 보낸다.** 번호를 붙이고 항목마다 ① 근거가 이미 정한 것 ② 내 읽기 또는 추천 ③ 달리 하면 달라지는 결과를 쓴다. "예"라고만 답해도 추천대로 되게 쓴다. 앞 답에 따라 생기는 질문은 그 답 뒤로 미룬다. 질문의 전제는 지금 대상·환경에 둔다. 남은 항목이 없으면 묻지 않고 `wf-build` 로 간다.
5. **답이 연 가지를 다시 편다.** 답을 받으면 그 답 때문에 새로 갈리는 결과(예: "기존 확정을 안내한다" → 그때 쓴 새 요청 ID 로 나중에 조회하면?)를 2~3처럼 펴고, 남으면 다시 보낸다.

## 끝 조건

2의 목록에서 3을 통과한 항목 가운데 사용자에게 보이지 않은 것이 없고, 보낸 항목마다 답(또는 추천 승인)이 있다. 지도에만 적고 사용자에게 보내지 않은 항목은 확인된 것이 아니다.

## 작업 지도 (결정·의존·완료 조건을 대화만으로 놓칠 위험이 있을 때)

- 위치는 `work/<작업명>/work.md`. 질문을 보내기 전에 쓴다. 끝나면 재사용할 결정을 반영하고 지도를 정리한다.
- `## 맥락`: 대상(저장소·경로·커밋)과 근거(경로·버전·용도: 현재 결정 / 과거 비교 / 연결 예), 범위 안·밖, 시나리오 전·행동·후, 위임별 작성권. 시작·대상 변경·재개·정정 때 바뀐 항목만 고친다. 위임·검토에 함께 넘기고, 비밀값·env 내용은 적지 않는다.
- `## 기준`: `요청 원문`(사용자 글 그대로, 결과·범위를 바꾼 후속 글 포함)과 요구 기록 표 `ID | 요구(입력→관찰 장소→기대) | 출처·위치 | 의존 | 확인 방법 | 상태`.
  - 출처(원문·사용자 결정·계약·조사 사실)가 결과 일부만 정하면 행을 나눠 나머지를 미정으로 둔다. 내 읽기가 출처인 행은 사용자가 확인하기 전까지 미정이다.
  - 상태는 확정·미정(사용자 답)·미확인(조사). 미정·미확인에 의존하면 확정이 아니다. 확인 방법은 요구를 어기면 실패해야 한다. 범위 밖은 넣지 않는다.
- 지도를 쓰거나 고친 뒤 `python3 .agents/skills/wf-verify/verify.py record --map <지도>` 로 형식과 남은 미정을 본다(waiting-user 면 묻는다).
