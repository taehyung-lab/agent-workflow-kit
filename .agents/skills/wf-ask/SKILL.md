# 요구 확인

실제 자료·계약에서 사용자 몫의 선택을 발견하는 책임이다. 선택이 남으면 조사·재현까지 하고 답 뒤에 구현한다. 이미 요청·계약이 결과를 정하면 다시 승인받지 않는다.

## 절차

1. **조사한다.** `python3 .agents/skills/wf-context/context.py inspect` 로 지금 대상(경로·커밋·변경)을 보고, 요청 원문과 AGENTS.md 「프로젝트 지도」가 가리키는 계약·환경 문서, 현재 동작을 읽고 실행해 본다. 조사로 알 수 있는 사실은 묻지 않는다.
2. **요청을 결과로 옮긴다.** 요청의 목표 문장을 구절로 나누고, 구절마다 "어떤 입력에서 사용자가 어디서 무엇을 보게 되는가"로 옮긴다. 옮기면서 내가 한쪽으로 읽은 것을 한 줄씩 적는다.
3. **새 동작이 받는 대상을 실제 자료에서 편다.** 이번 변경이 읽거나 바꾸는 자료를 열어, 종류나 상태가 다른 대상(쓰는 중·멈춘 것·끝난 것, 내 것·남의 것, 이미 처리된 것, 표기만 다른 것)을 찾는다. 그 대상을 요청한 흐름에 하나씩 넣어 본다: 처음 하기, 다시 하기, 순서 바꾸기, 이미 쌓인 자료. 대상마다 결과를 정하는 원문·계약의 문장을 찾고, 없으면 내가 정한 것으로 적는다. 지금 코드가 그렇게 동작한다는 사실은 새 동작의 근거가 아니다: 기존 동작을 깨지 않는 것은 지키는 것이고, 기존 동작을 새 기능의 규칙으로 삼는 것은 내가 고른 것이다. 범위는 이번 변경이 닿는 자료와 요청한 흐름까지다.
4. **별도 독자에게 읽힌다(대표 기록을 쓰거나 기존 자료의 처리를 바꾸는 작업).** [reader.md](reader.md) 전문 뒤에 요청 원문을 글자 그대로 붙여 하위 에이전트에게 맡긴다. 내 읽기·계획·지도는 넘기지 않는다. 독자가 낸 "정해야 할 것"을 2·3의 목록에 더한다.
5. **나눈다.** 적은 것마다 달리 정한 경우를 실제 흐름에 넣어 사용자가 받는 결과(정책·자료·외부와의 약속·범위·권한)가 달라지는지 본다.
   - 달라지지 않는다 → 구현 세부이니 지운다.
   - 원문·계약이 그 대상과 상황의 결과를 정한다 → 근거를 남기고 진행한다. 상위 종류에 대한 일반 문장을 특수 상태의 허용·보존 정책으로 넓혀 읽은 것은 근거가 아니라 내 해석이다.
   - 그 밖은 사용자 몫의 선택이다. 현재 코드가 하는 일과 내가 추천하는 일을 구별해 보여 준다. 표시·오류·출력도 다른 사용자가 읽는 계약이면 같은 기준으로 판단한다.

6. **목록과 보낼 선택을 대조한다.** 2~4에서 찾은 결과 중 5에서 원문·계약으로 확정한 것만 진행 근거로 둔다. 나머지는 현재 동작을 유지하자는 추천까지 모두 사용자 선택으로 보낸다. 각 선택에는 실제 자료, 달리 고르면 달라지는 결과, 추천과 이유를 적는다. 독립인 선택은 묶고 앞 답에 의존하는 것만 뒤로 미룬다. 근거가 이미 정한 사실은 확인을 기다리지 않는다. 목록의 모든 결과가 근거로 확정되어 남은 선택이 없으면 `wf-build`로 진행한다.
7. **답이 연 가지를 다시 편다.** 답을 받으면 그 답 때문에 새로 갈리는 결과(예: "연체된 책은 대출을 막는다" → 책을 반납하면 바로 풀리나?)를 2·3·5처럼 펴고, 남으면 다시 보낸다.

## 끝 조건

2~4의 목록에서 결과가 달라지는 항목마다 근거 문장 또는 사용자 답이 있고, 사용자에게 보내지 않은 선택이 없다. 현재 동작을 유지한다는 해석도 같은 기준으로 대조한다. 질문이 없거나 기록 형식이 맞다는 사실은 이 조건의 증명이 아니다.

## 작업 기록

결정·의존·완료 조건이나 여러 대상을 유지해야 하면 [map.md](map.md)의 대표 기록 하나를 쓴다. 원문과 후속 답은 도구에 그대로 전달하고, 요구 해석은 출처 번호로 연결한다. 이 기록은 같은 원문을 대상마다 복사하지 않게 하며, 중요한 선택을 찾아 주는 대신이 아니다.
