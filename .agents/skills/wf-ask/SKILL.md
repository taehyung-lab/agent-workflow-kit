# 요구 확인

이 단계의 산출물은 코드가 아니라 **사용자에게 보내는 이해 확인**이다. 사용자가 확인하기 전에는 제품 파일을 고치지 않는다(조사·재현은 한다. 무관해 보이는 부분도 먼저 구현하지 않는다).

## 절차

1. **조사한다.** `python3 .agents/skills/wf-context/context.py inspect` 로 지금 대상(경로·커밋·변경)을 보고, 요청 원문·계약·환경 문서·현재 동작을 읽고 실행해 본다. 조사로 알 수 있는 사실은 묻지 않는다.
2. **내가 정한 것을 전부 편다.** 요청의 목표 문장을 구절로 나누고, 구절마다 "어떤 입력에서 사용자가 어디서 무엇을 보게 되는가"로 옮긴다. 옮기려면 아래를 정해야 한다. 정한 것마다 한 줄로 적는다(계약이나 현재 코드와 맞는 것도 적는다).
   - 같음의 기준: "같은·중복·이미 있는"이 무엇이 같을 때인가(식별자가 같을 때인가, 사람·대상이 같을 때인가).
   - 범위: 누구·어느 자료·어느 경로까지인가. 이미 쌓인 자료도 포함인가.
   - 때와 순서: 언제 일어나는가. 동시에 하거나, 다시 하거나, 나중에 하면 어떻게 되는가.
   - 값과 한도: 근거 없는 숫자·기간, 외부가 읽는 형식.
   - 그대로 두기: 규칙이 없어서 지금 동작대로 두기로 한 것.
3. **사용 흐름에 대입해 거른다.** 항목마다 달리 정한 경우를 실제 흐름(다른 기기·다시 시도·이미 쌓인 자료·동시 사용)에 넣어, 사용자가 받는 결과(정책·자료·외부와의 약속·범위·권한)가 달라지는지 본다.
   - 달라지면 보낸다. 계약이 그 결과를 직접 말하면 계약대로 정하고 보내지 않는다. 계약의 용어를 원문의 다른 낱말에 내가 이어 붙인 것은 읽기이니 보낸다.
   - 달라지지 않으면 구현 세부이니 지운다.
   - 표시 문구·출력 형식·빈 화면·오류 안내처럼 사소한 표시는 묻지 않는다. 기존 화면의 방식을 따르고 완료 보고에 "이렇게 정했다"고 밝힌다.
   - 기존 보장(번호·기록 유지 등)은 지키는 것이지 묻는 것이 아니다. 사용자가 글자 그대로 말한 것은 다시 묻지 않는다.
4. **남은 항목을 한 번에 보낸다.** 번호를 붙이고 항목마다 ① 근거가 이미 정한 것 ② 내 읽기 또는 추천 ③ 달리 하면 달라지는 결과를 쓴다. "예"라고만 답해도 추천대로 되게 쓴다. 앞 답에 따라 생기는 질문은 그 답 뒤로 미룬다. 질문의 전제는 지금 대상·환경에 둔다. 남은 항목이 없으면 묻지 않고 `wf-build` 로 간다.
5. **답이 연 가지를 다시 편다.** 답을 받으면 그 답 때문에 새로 갈리는 결과(예: "탈퇴한 계정은 비활성화한다" → 그 계정의 이메일로 다시 가입하면?)를 2~3처럼 펴고, 남으면 다시 보낸다.

## 끝 조건

2의 목록에서 3을 통과한 항목 가운데 사용자에게 보이지 않은 것이 없고, 보낸 항목마다 답(또는 추천 승인)이 있다. 지도에만 적고 사용자에게 보내지 않은 항목은 확인된 것이 아니다.

## 작업 지도

결정·의존·완료 조건이나 대상·근거를 대화만으로 놓칠 위험이 있거나 사용자가 기록을 요구하면, 질문을 보내기 전에 [map.md](map.md) 대로 `work/<작업명>/work.md` 를 쓴다. 지도에만 적은 것은 사용자에게 보인 것이 아니다.
